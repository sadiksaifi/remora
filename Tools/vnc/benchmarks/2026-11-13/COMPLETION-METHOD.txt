Prospective completion control, version 2

Purpose
Measure first sampled ROI paint and completion of the eventual watched ROI excluding its fixed blinking-caret rectangle separately. This control does not measure whole-desktop completion, remote processing time, or the duration of the quiet period.

Plan frozen before live execution
Run exactly one matched round for each client in this order: Remora Apple/Screen Sharing mode, Remora standard VNC mode, Apple Screen Sharing client. Each round has 16 planned alternating forward/reverse rows for each action, in the order scroll, type, menu. Use the same host, endpoint, remote scene, window geometry, capture configuration and SETTINGS in round.py. Use a fresh J-prefixed label and output prefix for every client. Retain failures and every planned outcome recorded before a stop. Do not repeat or select rounds on latency or completeness. A failed round stays failed. Preserve all raw receipts.

This is a descriptive control with no confidence analysis, superiority inference, or selection. Publish both first-response and completion metrics and their sample counts, with explicit completion-null outcomes and first-response/guard failures. Do not replace or pool the existing six M paired rounds. Do not rewrite the failed standard-M attempt.

Shared change for all three clients
Use 1200 ms without stable sampled ROI change to establish each baseline and to accept each post-input settled ROI, with an 8000 ms deadline in both places. All physical events, their durations, ROI settings, action thresholds, input timestamp t0, first-response capture search and 3000 ms first-response deadline are unchanged from immutable J/latency.swift. All existing focus, interruption, persistence, round-trip and menu-precondition guards remain. Before any live control data, freeze one stability mask in window coordinates: x=160..<165, y=155..<175, rectangle 160,155,5,20. Ignore only those caret samples in baseline/post-input settling and matching a completion frame to the settled ROI. The menu ROI contains that blinking caret, which changes approximately every 500 ms; ignoring it prevents indefinite settling or measuring its phase. The type ROI starts at x=200 and scroll ROI starts at x=180, so neither intersects this mask. Apply this identical fixed mask to all three clients. Do not infer or change the mask from measured outcomes. First-response detection, action thresholds, first-change/settled semantic checks, round-trip checks, and the requirement that a completion frame differ from the pre-input ROI remain unmasked. The control adds failure guards for a missing matching completion frame or an unchanged final ROI when change is required.

Completion metric
After the eventual settled ROI is accepted, search retained frames in display-time order for the earliest frame with displayTime > inputTicks, stableChanged(frame.samples, settled.samples, grid) == 0, and changed(frame.samples, preInput.samples) >= threshold. changed() is the existing count of sampled luminance differences greater than 48. stableChanged() uses the same count except for the fixed caret rectangle; it converts Grid origin, column count and sampleStep from capture pixels into window coordinates using captureScale. Equality here excludes that fixed caret and uses the existing tolerance, not byte equality. Mismatched sample lengths or invalid grid column count fail closed with Int.max. completeObservedTicks is that frame's original SCK displayTime. completeLatencyMS is its interval from the original inputTicks. It does not add or time the quiet interval. The pre-input exclusion and action threshold prevent a pre-input or unchanged frame from becoming completion.

A transient forward menu opening whose eventual ROI is below the change threshold has null completion and diagnostic transient_menu_settled_closed. A reverse menu precondition already closed sends no input, retains its planned row, and has null first-response and completion fields. Neither outcome is zero latency. A changed final ROI without a matching retained frame is completion_frame_missing and stops the round. No settled observation retains null completion with its diagnostic.

Retention and images
Only this control retains up to 1800 sampled ROI arrays and trims 400 at overflow, leaving at least 1401 arrays. That retains approximately 11.67 seconds at the requested maximum 120 Hz, beyond the 3 s first-response plus 8 s settling deadlines; observed 60 Hz gives approximately 23.35 seconds minimum. Maximum sample storage at capture scale 1 is approximately 74.3 MB for scroll, 10.6 MB for type and 86.4 MB for menu, plus Swift allocation overhead. Frame image retention remains eight full images. Normal measurement does not convert trial images. With --save-trial-images, the first two observations retain the original before/first-change/settled PNG behavior and additionally save the exact completion frame and its line crop if still in imageHistory. Exact completion image unavailability is recorded explicitly and never substitutes a later frame.

Execution
Build: xcrun swiftc -O [private control source] -o [private compiled probe]
Run: python3 [private runner] --pid PID --window WINDOW --label Jcompletion-CLIENT
Do not add --save-trial-images to timed runs. Image-saving runs are semantic checks and image conversion affects their timing. The parent agent controls scene readiness, isolated test profile selection and live execution.

Validation before live execution
Compile the offline harness. Validate that caret-only changes are ignored for stability, genuine changes outside the rectangle are counted, fixed-mask boundaries are half-open, and length/grid mismatches fail closed; verify original changed() still counts caret changes. Validate normal completion, transient menu/no-input explicit null outcomes, and rejection of missing or impossible completion data through round.py's real validator. Compare unchanged physical-event and first-response code against the immutable J source. Record source hashes and a full source diff. No production files, installed app, live connection state or previous benchmark receipts are changed.

Observed outcome: Apple and Screen Sharing each completed 48/48. Standard completed 46 observed responses from 47 performed inputs and stopped on menu forward 14 with no response within the search deadline; later captures show the open menu. Reverse 15 was not attempted. All six semantic checks (two typing trials perclient) are excluded. No external native-test event was recorded during the control or calibration blocks. No failed round was replaced.
